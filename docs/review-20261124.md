## 3. P1（已知，待拍板）

### 3.1 RPC 半关闭丢回包

- 位置：`cbaselib/net/src/oi_tcp_channel.cpp:59-68`、`cbaselib/net/src/oi_net_session.cpp:25-28`、`cbaselib/net/src/oi_session_manager.cpp:758-783`。
- 触发：对端发完请求后 `shutdown(SHUT_WR)`（FIN），处理协程稍后 `co_return 0` 并回包。
- 现状：读到 0 后先交付已收字节，随即 `PassiveClose(0)`；因为 `0 != SESSION_MANAGER_NORMAL_CLOSE`，`CloseSession` 先 erase 会话并 `FailSession(CONNECT)`，处理协程之后的 `SendFrame` 按 sid 查不到，回包被丢。仓库内客户端不发 FIN。
- 后果：符合 HTTP 语义的外部客户端拿不到响应，handler 只看到连接失败。RST 与 FIN 只差错误码和日志，同样没有半关闭。
- 建议：二选一——明确不支持半关闭并写进文档/回归，或按 `ServerSession::PassiveClose` 的做法在 FIN 后延迟摘会话，补「发请求 → shutdown(SHUT_WR) → 仍收到回包」的回归。
- 置信度：确认（代码路径完整）；仓库内无触发客户端。

## 4. 新增 P2

### 4.1 批量 RPC 构建失败后的回滚会永久挂起

- 位置：`cbaselib/proto/inc/oi_rpc_coro.h:825-841`（回滚）、`cbaselib/proto/inc/oi_rpc_coro.h:378-398`（Dispatch 先置 `bDispatched` 再 Bind）、`cbaselib/proto/inc/oi_rpc_coro.h:817-819`（构造并 Submit）。
- 触发：`CallAll/CallMany/Notify*` 在 `RouteCall::Send` 里逐个构造并 `Submit()`；`Dispatch` 首行置 `bDispatched=true`，随后 `pGuard = make_shared`、`Bind`（`mSlots.emplace`、`AddSessionIndex` 的 `push_back`、`std::function` 复制）或请求对象拷贝抛 `bad_alloc`。异常被 `Send` 记为 `stBuildError`。
- 后果：回滚循环只判断 `bDispatched`，于是 `co_await` 一个 gate 仍为 `Idle`、从未登记到 `RpcCallManager` 的等待器；`Arm` 返回 true 永久挂起，`std::rethrow_exception` 永远到不了。调用方协程帧、请求副本和已提交请求的结果被永久保留，属于丢唤醒/永久泄漏。
- 依据：`iCallId` 只在 `Bind` 成功后赋值（412 行），失败路径保持 0；回滚条件没有检查它。当前回归没有分配失败注入，覆盖不到。
- 最小修复：回滚条件改为 `!stCall->bDispatched || stCall->iCallId == 0` 跳过；或把 `Dispatch` 从 `make_shared` 起整段包 try，失败时写 `stSubmissionError`、把 gate 置 `Ready` 再抛，让 `Arm` 不挂起。
- 验收：加一个可注入的分配失败点（测试钩子或自定义分配器），让 `Bind` 前的 `make_shared` 或 `Bind` 抛一次；`CallAll/CallMany` 必须在超时内以原异常返回，协程帧和等待项数回到基线；旧实现应表现为挂起/超时，用来证明用例有效。
- 置信度：代码路径确认；触发依赖分配失败，未实测。

### 4.2 变长容器解码按 4 字节/元素校验，嵌套元素放大内存

- 位置：`cbaselib/base/inc/oi_bytes_stream.h:243-264`（vector）、`280-304`（map）；示例协议 `modules/include/oi_rpcdata_alltypesdata.h:22-24`。
- 触发：对端在 `vector<Inner>` / `map<string, Inner>` 字段里声明很大的数量，每个元素只放 4 字节长度 0 的空 body。校验是 `iCount > RemainSize()/4`（map 是 8），只保证线格式下界，不约束本地 `sizeof(T)`。现有协议已有 `vector<Inner>`、`map<string, Inner>`。
- 后果：16 MB 字段对应最多约 4M 个元素；每个元素在本地展开成几十到上百字节的 `Inner`，加 vector 扩容峰值可达数百 MB；64 MB 帧可到 GB 级。对端可控，小内存机器会被 OOM killer 杀掉或长时间停顿；不是越界读写。
- 依据：`ReadPbContainer` 只按字段长度限制流，不设累计分配预算；`std::vector` 没有 `reserve`，峰值约为 1.5–2 倍。
- 最小修复：给解码增加累计分配预算（字段长度 + 元素数量 + 嵌套深度共同约束），或在 `operator>>(vector/map)` 按 `iCount * sizeof(T)` 设上限并分段拒绝；不要简单改成 `sizeof(T)` 下界，会误杀合法的「空元素数组」。
- 验收：构造 16 MB 字段、`count=RemainSize()/4`、每元素空 body 的包，断言解码在预算内失败并返回 `ParserException`/`OI_ERR_FAIL`，进程 RSS 不出现数百 MB 峰值；合法的大数组（例如 100 万个 `int32_t`）仍能解。用旧实现对照确认会吃内存。
- 置信度：机制确认；未实测分配峰值。

### 4.3 Windows 上 HTTP 大响应释放检查恒通过

- 位置：`modules/ipcclient/src/http_mgr.cpp:104-116`、`modules/ipcclient/src/http_mgr.cpp:118-139`；判定行 133。
- 触发：Windows 单/多线程 `hold` 用例的 `hold http release before=... after=...`。
- 现状：非 glibc 分支 `AllocatedBytes()` 直接 `return 0`，`iBefore == iAfter == 0`，`iAfter > iBefore + 8MB` 永不成立。客户端即使把 32×1MB 响应留在堆上，Windows 仍打印 `bad=0`。
- 后果：四路里的 Windows 两路对该性质没有覆盖，报告却显示通过；只有 Linux 有真实检查。
- 最小修复：Windows 用 `GetProcessMemoryInfo` 的 `PrivateUsage`/工作集，或在 harness 明确标记该检查在 Windows 未覆盖，不能算通过。
- 验收：Windows 上 `before/after` 为非 0，且旧实现「保留 32 MB 不释放」能让 `bad=1`；或脚本输出 `skipped` 并让 `--case all` 把它记为未覆盖而不是通过。
- 置信度：确认。

### 4.4 Linux 手动 hook 构建下 blocking-wake 的 trace 断言静默跳过

- 位置：`CMakeLists.txt:71`、`tools/regression/cases/db.py:27-32`、`tools/test_matrix.py:292-294`。
- 触发：Linux 单配置构建以 `-DOI_ENABLE_TEST_HOOKS=ON` 编译后，按 `docs/testing.md` 用 `--case blocking-wake --bin-dir deploy/bin` 运行。
- 现状：构建标记写到 `${CMAKE_RUNTIME_OUTPUT_DIRECTORY}/$<CONFIG>/oi_test_hooks.txt`，Linux 设了 `CMAKE_BUILD_TYPE=Release`，所以落在 `deploy/bin/Release/`；`bin_dir` 是 `deploy/bin`，`stamp.exists()` 为假，`trace_submit_to_worker` 等 7 项断言整段跳过，测试仍 PASS。矩阵在 Linux 强制 hooks=OFF，所以不影响 `--case all`。
- 后果：分段唤醒测量无法由手动 hook 构建产生可信结果；请求 hook 而标记缺失时也不失败。
- 最小修复：去掉 `$<CONFIG>` 子目录，或让 runner 显式接收标记路径；请求了 hook 而标记缺失时 fail。
- 验收：Linux 以 hooks=ON 构建并跑 `--case blocking-wake --bin-dir deploy/bin`，7 行 `wake benchmark trace_*` 必须出现；删掉标记文件后同一命令必须失败而不是跳过。

### 6.2 错误路径/资源

- HTTP 服务端缓冲响应超出发送额度时整包关闭、handler 无感知：`cbaselib/http/src/oi_http_server.cpp:526-535`；`SendBuffered` 在额度不足时不追加并返回 BUSY（`cbaselib/net/src/oi_session.cpp:41-44`）。文档已说明「超上限的单条消息被拒绝」（`docs/cbaselib.md:143-145`），但闭连接没有任何日志/错误码，建议至少记录并交给流式发送。
- redisserver 单个回包大于 `max_send_queue_bytes` 时丢弃并断连（`modules/redisserver/src/redis_server.cpp:206-235`）；`AppendReply` 先在 hiredis C 回调里整包物化（`147-197`），分配失败会抛 `bad_alloc` 穿过 hiredis/libuv 的 C 帧，属 UB/terminate 风险。redisserver 是内部测试进程，影响有限；建议对回包设上限、超限先回 `-ERR reply too large`，并在 `OnReply` 内 catch。
- HTTP trailer 解析每段重扫全缓冲（`cbaselib/http/src/oi_http_server.cpp:333-344`），1 字节慢速分段可放大到 O(n²)，占 poll 线程 CPU；头部扫描已有 `iScan` 记忆，trailer 没有。
- HTTP 客户端流式请求源结束后 2ms 泵继续空转（`cbaselib/http/src/oi_http.cpp:469-501`），慢响应/长轮询下纯唤醒开销；`bDone` 且无 sink 时可停泵。
- HTTP 客户端请求（头+正文）大于 `max_send_queue_bytes` 时直接 `OI_ERR_BUSY`（`cbaselib/http/src/oi_http.cpp:1236-1241`），文档未写「整包入队」语义，易误以为是服务端拒绝。
- UDP `sendto` 硬错误只记日志并丢包（`cbaselib/net/src/oi_udp_channel.cpp:190-196`），`SendBytes/SendFrame` 早已返回成功；TCP 同类错误会 `PassiveClose`，语义不一致。UDP 绑定口也没有解绑/释放路径（`cbaselib/net/src/oi_accept_channel.cpp:129-136`、`oi_udp_channel.cpp:99`），只影响停服/未来重绑。
- TCP 拨号无框架级超时（`cbaselib/net/src/oi_connect_channel.cpp:22-35`、`oi_session_manager.cpp:200-229`），黑洞地址要等 OS SYN 超时；`docs/coroutine.md:329` 已写明「不提供单独连接超时参数」，属已声明取舍，不按缺陷计。
- `db` 的 `PickOne`/`ToDbMap`/`AppendRowParameters` 未捕获 `ToJsonText` 的 `std::invalid_argument`（`cbaselib/db/inc/oi_db_row.h:436-457`、`cbaselib/db/inc/oi_db_json.h:7-12`、`cbaselib/proto/inc/oi_json.h:365-378`）；`[dbjson]` 含不可表示值时，返回 `int32_t` 的接口会抛异常，`Pick` 的「失败不改输出、返回 INVALID_ARGUMENT」承诺不成立。
- JSON 读入 `double` 不校验有限性（`cbaselib/proto/inc/oi_json.h:148-152`）；`1e999` 会以 ±inf 进入 `[dbjson]`/`FromJsonText`，与 `float` 分支不一致。写回 JSON 才在 `ToJsonText` 抛错。
- logd 静态表一条坏行放弃整表并每秒重试：`cbaselib/registry/src/registry_server.cpp:538-560`；首次即坏时 `m_bSnapshotOk` 永假，所有客户端每次 pull 失败；建议跳过坏行并记录行标识。
- logger 未连接累计超过 4 MB 或单条超 `LOG_FRAME_MAX` 时静默丢日志（`cbaselib/logger/src/oi_log_client.cpp:31-46`），`LOG_*` 丢弃返回码；`LogMgr::Pump` 在 logd 持续失败时 `m_iSent` 永不达标，`yield(0)` 死循环（`modules/ipcclient/src/log_mgr.cpp:72-87`）。框架侧建议加丢弃计数/首故障限频，测试侧加连续失败退出。
- TestBoard 异常路径不归零：`HoldMgr::Pump` 等无最外层 try/catch（`modules/ipcclient/src/hold_mgr.cpp:396-505`），`co_await` 重抛提交期异常时 `Done` 不再执行，runner 只能按超时杀进程，真实失败点和 `bad` 丢失。
- `PollUnregisterProbe` 手工 `NetOs_Close` 后未 `DetachSocket`，析构二次 close 同一 fd（`modules/ipcclient/src/blocking_mgr.cpp:554-561`、`cbaselib/net/src/oi_channel.cpp:11-16`）；MT 下 fd 复用窗口内可能关掉无关套接字。
- `CheckSyncOnLoop` 等 poll 回调无超时上界（`modules/ipcclient/src/redis_mgr.cpp:498-501`）；回调不来时测试永久挂起。
- db 驱动把 `prepare`/`bind` 的明确失败也算连接不健康并丢弃（`cbaselib/db/src/oi_mysql.cpp:191-197`），业务错误会反复重建 TCP/握手；属保守策略，代价是连接抖动，可只在结果不确定的失败上标记。
