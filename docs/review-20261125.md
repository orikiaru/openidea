## 2. 系统性隐患（建议优先）

### 2.1 libuv C 回调链缺统一异常边界

- 定时器路径已有保护，可作为对照（`cbaselib/timer/src/oi_timer_manager.cpp:164-176`，注释写明「处在 libuv 的 C 回调里，异常不能穿出去」）。
- 网络收发与 drain 路径没有保护：
  - `cbaselib/net/src/oi_poll.cpp:84-105`（`OnPoll` 直接 `DataIn()/DataOut()`）
  - `cbaselib/net/src/oi_session.cpp:88-106`（`SwapInBuff` 的 `Append` 与 `OnDataIn`）
  - `cbaselib/net/src/oi_poll.cpp:279-324`（`Drain()` 直接 `fnCall`）
- 具体可达点位（各自独立确认）：
  - logd 写盘：`cbaselib/logd/src/log_server_session.cpp:41-73` 的 `try` 只包 `deserialize`；`LogManager::WriteLog`（`log_manager.cpp:170-200`，`Bytes::Reserve/Append`、`list::emplace_back`）与 `DeferWrite`（`215-226`）在 `try` 外。
  - HTTP：`StreamBody::Produce`（`cbaselib/http/src/oi_http_stream.h:295-301`，uv_timer 回调）、`OnPlaintext`/`ConsumeChunks`（`oi_http.cpp:717,891`）、`RequestFrame::Read`（`oi_http_server.cpp:280,324`）的 `append`/`Append`。
  - redisserver：`OnConnect` 整段无 try、`OnDisconnect` 的 `ArmReconnect` 在 catch 外（`modules/redisserver/src/redis_server.cpp:238-272`）。
- 后果：分配失败或未捕获异常穿过 libuv C 帧，属 UB，通常 terminate。
- 最小修复：在 `Poll::OnPoll` 的 `DataIn/DataOut`、`Drain` 的 `fnCall` 外层统一 `try/catch(...)`，转为 `PassiveClose`/`ReportTaskError`，与定时器路径一致。
- 置信度：机制确认；触发依赖分配失败（窄）。

## 3. 新增 P2（框架 / 协议）

1. **ServiceTable 观察者是裸指针且无注销**（`cbaselib/base/src/oi_registry.cpp:88-98,246-253`，`cbaselib/base/inc/oi_registry.h:76,80`）
   - `Watch/WatchList` 只 push，全仓无 `Unwatch`；`Apply` 在锁外按裸指针调用 `ApplyService`。
   - `modules/ipcclient/src/test_blocking.cpp:311` 注册的是栈对象；被观察服务一旦发生实例变化就回调已析构对象 → UAF。
   - 置信度：机制确认；当前回归未触发（`blocking-probe` 无实例）。修复：增加 `Unwatch` 并在管理器析构时摘除，或改 `weak_ptr`/令牌。
2. **UDP EAGAIN 后立即重开写关注、无退避**（`cbaselib/net/src/oi_udp_channel.cpp:181-226`）
   - `Flush` 在 EAGAIN 时返回 true，`DataOut` 立刻 `ChangeEvents(IO_EV_WRITE)`。Windows 上 UDP 基本恒报可写，发送缓冲满时形成紧循环，poll 线程 100% CPU。
   - 置信度：逻辑确认；是否自旋依赖平台 POLLOUT 语义。修复：EAGAIN 用短 timer/本 tick 闸门退避。
3. **HTTP 客户端 chunked size 行完整时不限长**（`cbaselib/http/src/oi_http.cpp:657-672`）
   - 只在 `\r\n` 未到时检查 >1024；服务端对 `iEnd > 1024` 直接 400（`oi_http_server.cpp:302-306`）。超长全 `0` 行经 `ParseHex` 得到 `iSize==0`，被当成终止块，body 提前结束/状态错位。
   - 置信度：确认。修复：对完整行同样校验长度上限。
4. **logd 本地诊断日志被提前丢弃 + 日志客户端已连接发送失败不回退入队**
   - `cbaselib/logd/src/log_manager.cpp:181-191`：注释写「满时」才 BUSY，实际只要 `m_pResumingSession || !m_vWaitingSessions.empty()` 就丢本地日志（`pSession==nullptr`）。
   - `cbaselib/proto/src/oi_rpc_session_manager.cpp:195-223`：`SendRawOrPendResult` 已连接分支直接 `SendBytesResult`，返回 BUSY/CONNECT 时不回退入队；`cbaselib/logger/src/oi_log_client.cpp:45` 走此路径 → 断线/背压瞬间丢帧。
   - 置信度：确认。
5. **redisserver 把 RESP2 `*-1` 空数组改写成 `$-1`**（`modules/redisserver/src/redis_server.cpp:179-181`）
   - hiredis 把 `*-1` 与 `$-1` 都归为 `REDIS_REPLY_NIL`，代理统一回 `$-1`；BLPOP 等超时结果对严格 RESP2 下游变成 bulk null。
   - 置信度：转换确认；对非 hiredis 下游的影响为推测。
6. **poll 注册失败先关 fd、后 uv_close**（`cbaselib/net/src/oi_poll.cpp:765-777`）
   - `bInitialized` 时 `CloseWatchOnLoop(pWatch,false)` 后立刻 `NetOs_Close`；close 回调延后，fd 号在回调前被复用时 `EPOLL_CTL_DEL` 可能摘掉新连接注册。触发需 `uv_poll_start` 失败 + fd 复用（窄）。
   - 置信度：代码路径确认；后果需注入验证。
7. **`sid_t` 是 int32 直接自增**（`cbaselib/include/oi_header.h:43-44`，`cbaselib/net/src/oi_session_manager.cpp:672-674,748-753`）
   - 累计到 2^31 是有符号溢出 UB；回绕后新会话覆盖旧 sid，可能串号/投错连接。
   - 置信度：确认；触发需 2^31 级累计（超长运行）。修复：改 `uint64_t`。
8. **发送上限只校验到 SIZE_MAX**（`cbaselib/net/src/oi_session_manager.cpp:26-45`，`cbaselib/net/src/oi_tcp_channel.cpp:77`）
   - Windows `NetOs_Send` 把 `size_t` 截成 `int`；配置 >INT_MAX 且堆积 2GB 时单次发送失败并 `PassiveClose`（极窄）。
9. **BlockingWorkChannel 控制管道破裂后 EOF 空转**（`cbaselib/net/src/oi_blocking_work_channel.cpp:158-191`，`oi_fifo_channel.cpp:67-90`）
   - 写端关闭后读端 EOF 在 poll 上持续可读，`m_iInFlight != 0` 时不解注册，poll 线程空转到在途任务完成（罕见）。
10. **协程 `await_suspend` 是 noexcept 却做堆分配**（`cbaselib/base/inc/oi_coro.h:197-238`，`cbaselib/base/src/oi_coro.cpp:213-245`）
    - `Schedule/Post`、`DetachFinished` 的 `push_back` 可抛 `bad_alloc`，在 `noexcept` 中直接 terminate。OOM 才触发。

## 4. 新增 P2/P3（测试有效性）

- **wake_bench 分段求和断言代数恒真**（`modules/ipcclient/src/wake_bench.cpp:96-100,242-248`）：`(a-b)+(b-c)+… ≡ a-f`，分支永不成立，给出「分段守恒已验证」的假象。
- **web 用例 IPv6 环境阻塞只打印不生效**（`tools/regression/web.py:994-1001`）：无 IPv6 主机上仍无条件绑 `::1`，以裸 `OSError` 失败而非标记环境阻塞。
- **hold 的 `max_clients`/`idle_ms` 是死配置**（`tools/regression/cases/hold.py:92-96`）：两个键在产品配置/代码里都不存在，测试以为改了下限实际走默认值。
- **`test_matrix --mode st --asan` 用错构建目录**（`tools/test_matrix.py:323-324`）：ASan 传 `build` 而非 `mode_build`，st 未配置时必失败；Windows 上 `--asan`/`--clock-faults` 被静默忽略仍报绿。
- **clock 注入不校验是否生效**（`tools/regression/cases/hold.py:189-195`）：不检查 `.so` 存在/加载成功，无偏移断言，注入失效时仍 PASS。
- **`--platform both` 下 Linux configure 覆盖 Windows 的 hook 标记**（`CMakeLists.txt:71`、`tools/test_matrix.py:190-194,292-294`）：跑完后 Windows 侧 hook 状态与标记不一致，导致 disk-full/log-backpressure 假失败、blocking-wake 假通过。
- P3：`hold absolute deadline buckets` 接受 `buckets=0`（`hold.py:239`）；`run_web` 主断言只带 stderr、失败时丢 stdout 证据（`web.py:993`）。

> 「TestBlocking 与 TestDb 争抢 MySQL 阻塞池」（`test_blocking.cpp:380,443`、`test_db.cpp:747`）需要同时开 `Test.hold` 与 `Test.db`，而测试规程要求一次只开一个用例，**实际不触发，不计为缺陷**。
