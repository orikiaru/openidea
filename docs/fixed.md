### 已完成实现与断言

- **普通 TCP/RPC 按需接收与 HTTP 例外**：普通 TCP/RPC 默认接收上限由旧 64 MiB 收紧为 **1 MiB，含 8 字节 RPC 帧头**，请求和回包两端检查；首读 **4 KiB** 后按需增长，不预分配 1 MiB。HTTP 按用户选定策略保留原 `kMaxHeader + kMaxBody` 独立额度和 **8 MiB 普通正文限制**，不是把所有协议都统一成 1 MiB；逐协议限制尚未实现，见 [条件待办](<../todonext.md#a-等实际接入或先定合同>)。更早 Windows MT/Linux MT 的 local 断言仍期待旧默认值而实际失败，不能抹去；更新后的相关断言通过不代表最终清理通过。
- **容器解码 64 MiB 逻辑预算及容量边界**：旧实现仅以线格式的 4/8 字节元素下界检查数量，对端声明大量空嵌套对象可使 16 MiB 字段展开数百 MiB、64 MiB 帧达 GB 级。新行为对每个独立帧累计 **64 MiB 逻辑解码预算**，覆盖嵌套、多字段，事务回滚恢复预算，下一独立帧重置；估算包含元素对象与正文，不等于精确 RSS 硬上限，也没有用 `sizeof(T)` 替代线格式下界误拒合法空元素。已通过断言包含合法大数组、16 MiB 空 body 放大输入读取 count 后即拒绝且输出不变，以及非 2 幂 **6000** 容量压实/追加、超 1 字节保护；没有执行旧版 GB 级放大对照或声称测得 RSS 峰值。原证据与验收建议见 [11-24 review §4.2](<review-20261124.md#42-变长容器解码按-4-字节元素校验嵌套元素放大内存>)。
- **批量 RPC 构建/Bind 失败回滚**：旧行为在已置 dispatched 但 Bind 未成功、callid 为 0 时仍等待 Idle gate，原异常无法传回且协程永久挂起。新行为只等待真正登记的非零 callid，跳过未登记项；故障注入断言核对原 `bad_alloc` 返回、首项清理和登记等待恢复基线（该场景归零）。这是对应异常场景的业务验收，不推断所有 OOM 点均已注入。原触发、后果与替代方向见 [11-24 review §4.1](<review-20261124.md#41-批量-rpc-构建失败后的回滚会永久挂起>)。
- **coro 真实断言与失败退出**：旧应用把 `bad=0` 写死并直接成功退出，脚本只查日志字面量，协程数或计时为 0 也可假绿。现计数、计时及退出状态均参与验收，不再靠字面量。历史 Windows MT/ST 定向用例完成 10 万次挂起唤醒、100 万空任务并报告 `bad=0`，ST 的 held/wake/done 分别为 100000/100000/1000000；详见 [历史专项](<lasttesting.md#回归验收专项2026-11-25-早先历史记录本轮未重跑>)。**最新两轮矩阵均未重跑 coro**，不将历史专项当最新专项验收。旧行为和最初故障负例建议见 [11-24 review §2.2](<review-20261124.md#22-coro-用例仍然无法失败未修>)。
- **Windows HTTP 释放探针**：旧非 glibc 分支 before/after 恒为 0，保留 32×1 MiB 也可通过。现由测试钩子观察大缓冲释放次数和释放后容量，回归要求 **32 次释放、释放后容量仍至少 1 MiB 的次数为 0**，不将此等同 RSS/工作集精确测量。历史 Windows 故障负例保留响应缓冲，得到 `retained=63 bad=1`，证明该负例能失败；相关业务断言通过，最新 Windows MT 整路仍因 registry 清理失败而失败。旧假绿路径见 [11-24 review §4.3](<review-20261124.md#43-windows-上-http-大响应释放检查恒通过>)，专项见 [测试记录](<lasttesting.md#回归验收专项2026-11-25-早先历史记录本轮未重跑>)。
- **test-hooks 能力以实际二进制为准（合并历史 marker 同根项）**：原 Linux 标记落在额外 Release 子目录，手动 hook 构建可能静默跳过七项 trace；`--platform both` 又可能让 Linux configure 覆盖 Windows 标记。更根本地，configure 成功但构建失败时，新标记与旧产物不一致；Windows MT 曾实测只 configure ON→OFF→ON，标记变化而 ipcclient.exe SHA256 始终为 `7F17003649D5CBFE213AB34367D71783930358F1A5945899798361F6E8226BB2`，Linux 同机制当时未实测。现夹具直接运行实际可执行文件的 `--test-hooks` 查询，退出码 **40=关闭、41=启用**，不再用构建目录标记证明能力；Linux 两路实测两个程序均返回 40。更早 Linux ST hooks=ON 七项各 100000 样本、删除标记后失败是**历史 marker 批次**的有效性证据，不当作最终二进制查询分支的删除标记验收。原问题见 [11-24 review §4.4](<review-20261124.md#44-linux-手动-hook-构建下-blocking-wake-的-trace-断言静默跳过>)、[11-25 测试有效性](<review-20261125.md#4-新增-p2p3测试有效性>)。
- **matrix ASan/ST 目录与 Windows 参数拒绝**：旧 `--mode st --asan` 把 MT build 传给 ASan，可能用错/缺配置目录；Windows 的 `--asan`、`--clock-faults` 原来静默忽略而可假绿。现按线程模式选构建目录，并在原生 Windows 明确拒绝不支持参数。此处归档目录选择及拒绝语义，不是宣称最新 ASan 已跑；**最新两轮未重跑 ASan**，旧 `-st-st` 缺 OpenSSL 头构建失败仍保留在 [测试边界](<lasttesting.md#最终排版后复验2026-11-25历史记录>)。原问题见 [11-25 测试有效性](<review-20261125.md#4-新增-p2p3测试有效性>)。
- **HTTP chunk-size 长度/CRLF 一致与 Connection close 优先**：旧普通客户端完整行不限长；服务端 1024 字节正文后的 CR 单独到达拒绝、CRLF 同到却接受，流式客户端又把 CRLF 计入上限。Windows ST 修复前实测 1024 字节整包返回 200、分段在 LF 前返回 400；这些是旧行为，不是当前待测结论。新行为三条解析路径统一按**不含 CRLF 的 1024 字节**限额，1023/1024/1025 与整包/拆 CRLF 纳入断言。旧普通响应多行 Connection 可由后来的 keep-alive 覆盖 close，Windows ST 旧行为曾 9 次复用同一连接；现只要任一字段含 close 就优先关闭，不因后续 keep-alive 返池。相关修复断言已通过；不把旧记录「仍需测 1023/1025、其他平台」继续作为活动未完成，也不把最终 Windows MT 清理失败改写成整路通过。原长度问题见 [11-25 review §3](<review-20261125.md#3-新增-p2框架--协议>)。
- **hooks 不自动恢复的文档口径**：原文同时称矩阵会自动恢复 hooks、又记录 `restore_skipped=true / restored=false`，与实现不一致。现按实际行为说明**只设置、不自动恢复**，手动运行/交付前须显式重配 OFF，不是新增自动恢复能力。原矛盾见 [11-24 review §6.4](<review-20261124.md#64-文档>)。

## 2026-11-21 已定策略

- **直连断线不暂存**。`ProtoClientManager` 只在第一次连上前暂存 `Call` / `Notify`。已经连过再断，直接返回 `OI_ERR_CONNECT`，不补发。路由和多连接仍暂存补发。
- **UDP 空闲回收丢掉未发出的包**。超过 `idle_timeout_ms` 没收没发就关会话。待发队列里还没 `sendto` 出去的包随会话丢掉。入队成功不保证送达。
- **只传请求的 `RpcCall` 继续留着**。单次调用的主力仍是带回复对象、返回 `int32_t` 的那套。得到 `RpcResult` 的那路不删，新代码不用它当主力。
- **客户端拒绝重复 Content-Length（含 304，既定策略核对）**。第二次长度头按协议错误拒绝，数值相同也拒绝，304 同样按此规则处理，不是遗漏或本次新修复；和服务端一致。`hold` 的 `length-duplicate` 用两份 `Content-Length: 2` 锁住；旧行为会把它当成正文 `ok`。

## 2026-11-21 审查问题修复

以下记录本轮实现和已观察的业务验证。跨平台、线程模式的完整验收结果另见测试记录；未列出未运行的场景。

- **TLS 密文背压**：发送额度不足时保留尚未入队的密文，额度释放后继续发送，不把 BUSY 写成永久错误。握手已完成但密文仍未入队时，新明文先进入待发缓冲，不把这次发送判失败。HTTPS 真实收发覆盖受限发送额度和 65536 字节正文，核对原请求完整回包；不代表所有 TLS 失败路径均被注入。
- **RPC 收包异常**：分发抛异常时记录原因并关闭受影响的流连接，避免继续使用不完整批次。故障注入时两个请求同时在途，首个调用失败、延迟响应的第二个调用得到断连错误，连接关闭且保护计数归零（`first=1/-1 second=1/-3 close=1 guard=0`）；测试未证明两个回包处在同一次接收批次。
- **连接补发异常**：逐项隔离待发请求的发送和完成回调异常，后续待发项及重试决策仍执行。注入完成回调异常后 8 项均得到完成，保护计数归零。
- **注册中心断线与重载交错**：按 owner 排除已经撤销的旧登记，并保留重载期间新登记和其他来源的数据。真实 Redis 代理交错测试核对撤销失败与重载后 Pull：旧 owner 不再出现，其他来源地址仍可见。
- **注册中心地址分隔校验**：登记前拒绝含空白的地址字段，避免空格分隔的存储格式被拆错；测试检查拒绝及原快照不变。
- **logd 跨日顺序**：日志和轮转标记按接纳顺序入各级队列，写线程先处理旧批次再切换。Linux 的虚拟时钟加慢写回归逐行核对日期目录与标题；同一用例在旧实现下观察到旧日标题落到新日目录。
- **logd 跨日磁盘操作**：建目录、打开、刷新和关闭在写线程完成。新文件打不开时留下原因并继续写当前文件，进程不退出；旧文件刷新或关闭失败仍停止进程。Linux 注入次日路径为普通文件，确认进程仍在且 stderr 有失败原因，再正常停掉。另用受控慢打开闸门期间发真实畸形帧，观察 poll 处理并关闭连接，放行后核对会话日志落盘。这两项注入目前仅 Linux 覆盖。
- **HTTP 流与半帧计时**：流的无进度使用独立空闲时限，不再把流式处理按普通半帧计时；回归让 sink BUSY 800 毫秒跨过 500 毫秒半帧时限，并核对最终响应。持续无进度与持续进度按各自计时语义处理。
- **HTTP 服务端空闲连接**：首字节前和完整响应后的空闲连接按独立空闲时限关闭，真实连接回归分别验证两种情况；活动处理和待发送数据不按普通空闲关闭。
- **HTTP 客户端 trailer 上限**：缓冲式 chunked 响应累计检查 trailer 上限，回归覆盖边界和超限，并检查调用结果。
- **HTTP 客户端畸形头**：无冒号的响应头按协议错误拒绝，回归同时检查错误结果和后续新连接。
- **HTTP 正文与接收容量**：普通请求正文增量消费，合法正文不再要求一次全部留在接收缓冲；回归在 131072 字节接收容量下，以普通固定长度和单 chunk 分别收发 524288 字节，并核对超限请求返回 413。
- **生成器声明与字段校验**：拒绝不支持的自由类型及非法声明、越界枚举，保留合法协议；生成器检查覆盖有效输入和错误输入，未把历史 `long` 的具体旧编码路径推断为已验证。
- **限定名 Bytes**：对裸名及已限定名分别生成正确类型，避免重复命名空间；生成器检查覆盖两种输入。
- **component 解析**：文本入口填充组件生成表，组件声明不再因缺表项误报；生成器检查包含合法和非法声明。

## 已修复：RPC 超时扫描异常隔离

超时扫描逐项捕获完成回调异常，继续完成同批等待者。回归登记 128 项同一截止时间的等待，首个回调确认同批至少还有一项后抛异常，检查所有结果为超时、128 次回调及 guard 归零。独立副本恢复旧行为后，Windows 多线程定向回归如预期失败，实得 `callbacks=1 same_batch=1 guard=127 bad=128`。

- **双平台矩阵丢 Windows 自定义参数**：`test_matrix.py --platform both` 把 `--define` 同时传给 Windows 子命令。
- **并行矩阵中断遗留子进程**：`parallel_matrix.py` 在启动与等待外补 `try/finally`，只回收本进程拉起的 lane。
- **TCP 监听后登记失败不回滚**：`StartServer` 在 `Publish` 失败时调用 `AcceptChannel::StopAccept` 关掉监听并释放端口，析构走同一路径。`rpc-ingress` 用带点的服务名迫使登记在监听之后失败，核对退出码 `-6`、没有 `ipc server listen`，随后的正式进程绑上同一端口。
- **反向 Hold 分支无覆盖**：客户端注册 Hold 接收端并用 mark `-2147483598` 触发服务端反向调用，断言客户端 `hold reverse trigger ... bad=0`、`hold reverse request served delay=1000` 和服务端 `hold reverse reply bad=0`。

验证：以上改动随后在 2026-11-21 的四路 `--case all`（Windows MT/ST、WSL Linux MT/ST）中复测。登记失败回滚的注入、TLS 明文暂存和跨日打开失败保持进程，在同日稍后的四路全量（Windows MT/ST、远程 Linux MT/ST，22/22）里再核对过；结果见测试记录。

## HTTP 消息能力（已全部完成）

对照 [libhv HttpMessage.h](https://github.com/ithewei/libhv/blob/master/http/HttpMessage.h) 的消息接口，当前提供请求/响应、原始正文和可重复 header；不以接口名称相同或数量相等作为兼容承诺。以下按需求独立实施并保留既有接口，均已验收。

- [x] **Cookie**：提供解析与构造能力；以多个 Set-Cookie、大小写与空值、转义往返验收。Cookie 属性至少覆盖 domain、path、expires、max-age、secure、httponly 和 SameSite；自动 cookie jar 单独决策，不隐式跨请求保存。
- [x] **重复 query**：提供解析与构造能力，明确多值顺序及缺失值语义；以重复参数、空值和转义往返验收。
- [x] **URL 编码表单**：支持 `application/x-www-form-urlencoded`，明确重复字段、空值及尺寸上限；以真实服务往返、边界拆包和空字段验收。
- [x] **multipart 表单**：支持文本及文件字段，明确重复字段、二进制内容和尺寸上限；以真实服务往返、边界拆包、空字段和文件内容字节一致验收。JSON 继续使用现有 JsonCpp 和 rpcdata 能力。
- [x] **流式收发**：提供分段读取、写入及背压，定义取消、超时、断连和资源生命周期；以大文件分段收发、慢消费者、断连和内存上限验证。流式路由按片消费正文；普通缓冲路径仍按完整正文处理。
- [x] **客户端 HTTPS**：提供证书链和主机名校验；本地可信 CA、错误主机名、不受信任证书、握手超时与连接关闭由 Web 回归覆盖。证书管理与部署单独设计。

服务端 TLS 由 Nginx 等反向代理终止，代理与后端之间走 HTTP，本项目不实现服务端 TLS。

libhv 消息还提供文件、JSON、类型化值等便捷接口；是否引入以实际需求为准，不影响上述阶段的验收。
